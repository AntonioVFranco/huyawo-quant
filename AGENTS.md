## Git checkpoints and reporting

- Use an approved GitHub integration first, protected provider-managed credentials second, and a protected, fine-grained minimum-privilege PAT only when necessary. Verify capability for the exact repository and operation. Keep credentials transient and out of chat, URLs, config, arguments, logs, commits and evidence. Use applicable cleanup on success, failure and interruption.
- Proceed with a routine checkpoint under existing task and standing project authority when scope, validation, evidence and publication gates are met. Review exact staged paths, bytes and modes under RFC-QUANT-0027 before committing, then review the exact outgoing content before an authenticated normal push. Keep private evidence and artifacts outside public Git. Obtain separate explicit founder approval for high-risk governance or source changes, scope expansion, exceptional publication or release, protected historical mutations, paid execution and destructive operations. Route high-risk changes through PR review. Honor branch protections. Never force-push or overwrite concurrent work.
- Independently read the exact destination branch ref after a push attempt and require equality with the intended SHA. If approved authentication is unavailable or synchronization fails, is ambiguous or cannot be verified, preserve any existing commit, report `BLOCKED_REMOTE_SYNCHRONIZATION` when required synchronization is incomplete, and inspect the remote before retrying the same commit within scope. Stop on divergence.
- Report directly in Codex chat using `OBSERVED`, `DERIVED`, `HISTORICALLY_REPORTED`, `PROPOSED` and `UNKNOWN`. Include source, runtime, configuration and instruction identities, authority, exact changes, commands and results, evidence and custody, milestone and attempt status, local commit, push attempt and result, remote SHA, PR, blockers, and exact next authorized action. Use Brazilian Portuguese for founder-facing communication and English for engineering prompts.
